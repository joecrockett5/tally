# Assumptions and decisions

One line of reasoning each. Grouped by area.

## Platform

- **.NET 10 (LTS)** — latest LTS at the time of writing (10.0.402 SDK).
- **PostgreSQL 18** (`postgres:18-alpine`) — current stable major on Docker Hub; there is no 19 image yet.
- **Minimal APIs** grouped per feature rather than MVC controllers — less ceremony, idiomatic for .NET 10, still "ASP.NET Core Web API".
- **xUnit v3 + Testcontainers.PostgreSql + WebApplicationFactory** — real Postgres for search/FTS/trigram behaviour; one container shared per test collection for speed.
- **Node 24 LTS** in the build stage.
- **Healthcheck runs the app binary** (`dotnet Tally.Api.dll healthcheck`) instead of adding curl to the runtime image — no extra packages.
- **ForwardedHeaders trusts any proxy by default** (`KnownProxies`/`KnownIPNetworks` cleared) because the container only listens on a private Docker/LAN network behind NPM; documented in README.

## Frontend

- **Plain CSS with custom properties**, no component library — the UI is small and mobile-first; avoids a heavyweight dependency.
- **Recharts** for charts — the brief's suggestion, declarative and React-native.
- **react-router** for navigation and a tiny typed `fetch` wrapper instead of a data-fetching library — fewer dependencies.
- **vite-plugin-pwa** (Workbox `generateSW`) for the service worker, caching only the app shell; `/api/*` is never cached.
- **Icons generated by a stdlib Python script** (`tools/icons/make_icons.py`) — tally-mark glyph, no image tooling needed.
- The service worker precaches only the built app shell (HTML, JS, CSS, icons); `/api/*` and `/healthz` are excluded and never cached. It auto-updates; `index.html`, `sw.js` and the manifest are served `no-cache`, hashed `/assets/*` as immutable.
- An offline banner explains that Tally needs a connection; there is no offline queue (out of scope).
- Npgsql's GSSAPI probing is disabled in the compose connection string (`Gss Encryption Mode=Disable`) because the runtime image has no Kerberos libraries and the database is on a private Docker network.
- The client computes "today" in the **server's configured timezone** (from `/api/config`) using `Intl`, so all devices agree on the diary day.

## Profiles

- Active profile is sent as **`X-Profile-Id`**; missing → 400, unknown → 404 (the SPA then returns to the picker).
- Avatar is an emoji plus a colour picked from a fixed palette; a random pair is chosen on creation.
- When a profile is deleted, its **shared foods stay** with `OwnerProfileId` cleared, so they remain visible but nobody can edit them; the creator's name is kept for display.
- Profile deletion hard-deletes private foods; recipe ingredients/saved-meal items of *other* profiles that reference those foods cascade away (only possible for foods that were shared then unshared — a rare edge case).

## Nutrition data

- **Nutrients stored as `double precision`**, nullable; rounding only at display (kcal integer, grams 1 dp).
- kJ/kcal derived with 4.184 when only one is present; salt = sodium × 2.5 when only sodium is present. Applied on every write path (OFF, CoFID, manual, import).
- **Portion-only foods** use basis `PerPortion` with a `PortionName`; servings for them are multiples of a portion. No weight is invented.
- **Diary entries snapshot per-basis nutrients** (plus food name/brand/source) and the quantity; totals are computed from the snapshot, so editing quantity later still uses the original values.
- Food deletion by its owner is a **soft delete** so their recipes and saved meals keep working; diary entries are unaffected anyway (snapshots).
- **Totals with unknowns**: a nutrient's total sums known values and is flagged *incomplete* if any entry lacked it; the UI shows a "+?" marker.
- Macro split uses UK label factors: protein 4 kcal/g, carbohydrate 4 kcal/g, fat 9 kcal/g.
- **"Days on target"** = logged days whose energy is within ±10% of the energy target and that did not exceed any upper-limit target (sugars, saturates, salt).
- Progress colours: targets (energy, fat, carbs, fibre, protein) are green within 90–110%, neutral below, amber above; limits (sugars, saturates, salt) are green below 90%, amber 90–100%, red above 100%.

## CoFID

- Source: *McCance and Widdowson's Composition of Foods Integrated Dataset 2021* (OGL v3), sheets 1.3 Proximates and 1.4 Inorganics, converted by `tools/cofid/convert.py` to `data/cofid/cofid-2021.csv` (2,887 foods). The xlsx itself is not committed.
- CoFID 2021 reuses code `13-669` for two foods (roasted aubergine and raw watercress); the converter joins sheets on (code, name) and gives the second one code `13-669-2`.
- CoFID "Tr" (trace) → 0, "N" (not measured) and blanks → null.
- **Fibre uses AOAC fibre** (the UK labelling method) **and falls back to NSP** (Englyst) when AOAC is absent; the method is kept in the CSV. NSP reads lower than AOAC — documented, accepted for generic foods.
- Salt = sodium (mg) ÷ 1000 × 2.5. CoFID carbohydrate is "available carbohydrate" (excludes fibre), matching UK labels.
- CoFID is **seeded automatically on startup when the table is empty**, and can be re-imported (upsert by food code) with `dotnet Tally.Api.dll import-cofid`.

## Open Food Facts

- Checked the OFF docs (Oct 2026): **product lookup uses API v3** (`/api/v3/product/{code}`); **text search uses Search-a-licious** (`search.openfoodfacts.org/search`) because the v2 search API has no full-text search and `cgi/search.pl` is legacy.
- Published limits: product reads 15/min, search 10/min per IP. Tally enforces **instance-wide token buckets** (15/min, 10/min), backs off exponentially (30 s → 10 min) on 429/5xx/timeouts, and reports "online results unavailable" while backing off.
- OFF has no per-country nutrition fields, so "prefer UK fields" means: rank `en:united-kingdom` products first, prefer `product_name` for English-language products (else `product_name_en`), use `salt_100g` over sodium, and keep both kcal and kJ as labelled.
- Products sold only in the US/Canada are flagged **`CarbsMayIncludeFibre`** (US labels report total carbohydrate); values are stored as provided and the UI shows a note.
- Every fetched product (from barcode lookups *and* search hits) is upserted into `Food` with `FetchedAt`; stale products (default 30 days) are served from cache and refreshed by a background worker.
- Barcode misses are cached for 24 h (configurable). Search results are cached per normalised query for 24 h (configurable) to stay within limits.
- Barcodes are normalised: UPC-A (12 digits) is stored as EAN-13 with a leading 0; UPC-E is expanded to UPC-A first.
- Client debounces local search at 200 ms and online search at 600 ms (min 3 characters).

## Restaurants and import

- Restaurants are a **global list of names** (not private), created on demand when an item names a restaurant; items under them follow the normal private/shared rule.
- Labels: item with a restaurant → "Restaurant"; otherwise own item → "Mine"; someone else's shared item → "Shared".
- **Import is stateless**: preview and commit both post the file contents; commit re-validates and inserts valid, non-duplicate rows. Duplicates = same restaurant + name (case/space-insensitive) among foods visible to the profile, same barcode, or repeated within the file.

## Diary

- Diary date is a Postgres `date` (local calendar day). Timezone defaults to `Europe/London` (`TALLY_TIMEZONE`).
- "Copy meal" copies the **snapshots** of the source entries (it's a copy of what was eaten), not fresh food values.
- Recent = last 20 distinct foods/recipes logged; Frequent = top 20 by count over the last 90 days.

## History and export

- CSV export uses ISO dates (`YYYY-MM-DD`) so the file sorts and imports unambiguously; the UI uses DD/MM/YYYY. Unknown nutrients are blank cells, values have up to 3 decimal places, and a UTF-8 BOM is included so Excel reads "£"/accents correctly. Text cells that start with `= + - @` are prefixed with `'` to prevent formula injection.
- History ranges are limited to 366 days per request. Charts use the validated categorical palette (slots 1–3) with direct labels and a table view for the macro split; the energy chart has a "day by day" table equivalent.

## Recipes and saved meals

- Recipe nutrition is **computed live from ingredients** when viewed and **snapshotted when logged** (per serving, or per 100 g if a cooked weight is set and the user logs by grams).
- Recipe ingredient amounts are in the ingredient food's basis units (g, ml or portions); ml is treated as weight-neutral (no density conversion) for cooked-weight maths.
- Saved-meal items store food/recipe reference plus quantity; logging takes **fresh** snapshots from current food values.
